# AGENTS.md — building games with lcc-playable

You are helping a developer turn an XGRIDS LCC scene (a real place captured as 3D Gaussian Splats) into a browser game. Work from the repository root. API reference: `docs/api.md` (core: `lcc-playable`; optional gameplay helpers: `lcc-playable/kit`). Game type notes: `docs/game-types.md`. Frame rate and memory: `docs/performance.md`.

## Workflow
1. **Setup** (once): if `vendor/lcc-web-sdk/lcc-sdk-three.js` is missing, run `npm install && npm run setup`.
2. **Scene**: `npm run scene -- list`. If there are no scenes, ask the developer for one: a scene they own, or an XGRIDS sample scene from https://developer.xgrids.com/#/download?page=sampledata (downloading needs a login). Do not download scenes yourself. **They are for testing only and are not licensed for commercial use**; for anything shipped the developer needs scenes they have rights to. Import with `npm run scene -- add <folder-or-zip> --name <name>`. How developers get scenes: `docs/get-scenes.md`.
3. **Ask only if needed**: if the request does not say what the player does or how a round ends, or it conflicts with the scene (check `info` first), ask up to 3 short questions with a recommended answer each. Otherwise decide, and say what you decided at the end.
4. **Look at the scene** (about 5 minutes): `info` (read its `data` checks: tell the developer about every `warn`), `route --save .cache/route.json`, `plot .cache/map.png --points .cache/route.json` (read the image), then 3–5 `shot --out .cache/shots`s along the route at 1.5–3 m height to see the landmarks (take camera positions from route points, or snap them with `at`/`nearestWalkable` + 1.6 m: a camera inside a tree or wall gives a blurry image). Put landmarks and goals where `clearanceAt ≥ 0.3`, outside buildings unless the route clearly goes in: doorways often have clearance 0 and a Walker cannot pass them. Keep scratch files in `.cache/` (git-ignored), not in the repository root. See "Scene CLI" below.
5. **Start from an example**: `npm run new -- <id> --from <explore|runner|fps|flight> --scene <name>`, then edit `games/<id>/main.js`. Keep the structure: `createPlayable` → setup → `onStart` / `onUpdate` → `setAutopilot` → `p.run()`.
6. **Check** after every change: `npm run check -- games/<id>`, and `npm run check -- games/<id> --auto` for a full autopilot round. Fix `errors` first. Read the screenshots it lists.
7. **Deliver**: tell the developer to run `npm run dev` and open `http://localhost:8091/games/<id>/` (a server you start in your own session may stop when the session ends), and give the controls, route length and round time, `coverage`, and known issues. `npm run build -- games/<id>` makes a deployable folder in `dist/<id>/` (the SDK may be redistributed with it; on deployed sites it shows a small XGRIDS watermark because no appKey is set, which is expected).

## Rules that make games look right
- **The scene is the star.** Players chose this place. Take them through all of it: build tracks and levels along `p.geo.route()` (the path the capture person walked, past every landmark, where splats are sharpest). Aim for `coverage.trackCover ≥ 0.5` (scenes without a trajectory: `trackCover` is null, aim for `areaCover ≥ 0.3`) and rounds of 45 s or more (arena games such as the FPS example are the exception: one open area, short replayable rounds). Do not shrink the game to a small flat corner; adapt the game to the scene instead (narrow parts → single lane, steps → jumps).
- **Stay near the capture path.** More than about 10 m away from it, and high above it, splats get blurry and broken. Fly low (the flight example keeps 5–8 m over the route).
- **Real scale.** People are 1.7 m. Use `p.geo.groundAt`, `walkable`, `nearestWalkable`, `findPath` for every placement. Never guess coordinates or heights. Z is up, units are meters.
- **Things stand on the ground.** Give characters and props that move a shadow (`shadow(p, obj)` from the kit; `collectibles` and `patrol` do it for you). Without one they look like they float over the splats. By default it is the object's own animated silhouette. Set `sun` to the direction the shadows in the captured scene come from (look at trees and buildings in a screenshot) and use the same `sun` for every shadow in the game. Use `shape: 'disc'` for many small things (pickups, debris): only 64 figure shadows fit per game and each costs a draw.
- **Characters are rigged models**, never boxes or capsules: `loadCharacter('human' | 'robot')`, or a `.glb` URL the developer provides. Animations advance automatically; `Walker` picks idle/walk/run/jump. If you move a character yourself, call `ch.play('run')` etc. A character that moves without a matching action looks like it is floating.
- **Controls like a modern action game.** Third person: the mouse (pointer lock) or a touch drag turns the camera, WASD moves relative to the camera (`walker.update(dt, { yaw: cam.yaw })` with the default `FollowCamera`). First person: `FirstPersonCamera`. Never turn the camera or the player with A/D or arrow keys while walking: it makes players dizzy. Only on-rails games (runners) and vehicles steer with keys. Write the controls on the title card.
- **The camera must never be blocked.** Use `FollowCamera` (scene rays + fading props) or `FirstPersonCamera`. Put every game object in `p.props` so it fades when it blocks the view.
- **Routes need solid ground.** Tracks and paths use `makeRoad` (opaque, follows the terrain, merges where the route overlaps itself). Do not place obstacles where `road.shared(s)` is true.
- **Dark blobs in the sky** are floating splats in the captured environment, not your bug. If they are in view, `createPlayable({ sky: 'plain' })` replaces the captured sky with a gradient (tell the developer).
- **Show props only near the player** (about 40 m): meshes do not occlude correctly behind distant splats.
- **In-game text in the developer's language and script** (e.g. Simplified Chinese if they write Simplified Chinese).
- **Keep 60 fps.** `p.raycastSplats` costs 10-15 ms per ray: a few per second at most, never in a per-frame loop. Leave `pixelRatio` at 1 and `adaptive` on. Check `fps` in the check output and `p.quality.steps` (> 0 means the game was too slow and lowered quality). Adaptive quality only reacts to frames over 20 ms, so 45–60 fps with `steps` 0 is normal for large scenes: compare with the unchanged example on the same scene (`npm run new -- t --from explore --scene <name>`); if it is just as fast, it is the scene, so report it instead of chasing it. `?debug` (or the ` key) shows fps, frame time and main-thread time on the page; tell the developer about it when they report lag.
- **Use the kit (`lcc-playable/kit`) before writing your own props**: `placeAlong` + `collectibles` for pickups, `beacon` for destinations, `label` for signs (any language), `route.sample(s)` / `route.every(m)` for positions along the route, `minimap` for a map with markers, `patrol` for NPCs that walk around, `p.best` (kept for you) for high scores.
- **Keep the format credit.** The loading screen shows "Data Organization Format originated from XGRIDS" (required by the LCC2 White Paper license). Do not hide or remove it, and keep it in a custom loading screen.
- **Built-in texts** (Play, Paused, You win!) follow the developer's language: `createPlayable({ strings: { play: '开始', ... } })`.
- **No external assets or CDNs.** Props from three.js geometry with `toon()` + `outline()` materials; sounds from `sfx()`. Do not add npm dependencies.
- **Do not call** `LCCRender.setWriteDepth(true)` or start your own `setAnimationLoop`; game logic goes in `p.onUpdate` and runs only while `p.state === 'playing'` (pause and end cards then work without extra code).

## Checking your work
- Every game needs an **autopilot** (`p.setAutopilot`) that plays through the same input as a player (`p.input.setMove`, `setHeld`; `Navigator` for walking). It must really dodge, aim or steer. No invincibility, no teleporting to the goal. `npm run check -- games/<id> --auto` must end with `state: "won"`.
- Set `p.playArea` (track centerline or level points) so `check` reports `coverage`.
- Put the numbers you want to verify in `p.info`; read them with `--eval "p.info"`.
- Look at the screenshots: road visible, character visible and animated (legs in different poses across shots), props readable, nothing floating or sunk.
- Test the real controls too, not only the autopilot: `--eval 'p.input.setMove(0, 1)'` then sample `p.player.position` and `p.player.character.action`; check the animation runs (`p.player.character.mixer.time` grows).
- **If you cannot read images**, check with data instead and say so: positions vs `p.geo.groundAt`, `camera.blocked` in the check output, the character's `action`, the autopilot result.
- **Round length vs. check time.** `--auto` waits 300 s of real time by default, which runs 10–20% ahead of `p.playTime`. Autopilots with `Navigator` run at 6.5 m/s: a 1 km route takes about 160 s. Long captures (campuses: 2 km) need a shorter section (`route({to})`), or a higher `--timeout`. Scale time limits with the route length instead of fixing them.
- Budget: about 30 minutes to a first playable version. If a command runs over 30 s with no output, try a different approach.

## Scene CLI (`npm run scene -- <command> <scene> ...`, JSON output)
`list` · `add <folder|zip> --name n` · `info` (size, walkable m², trajectory segments) · `route [--seg N] [--from m --to m] [--save f]` (length, steps, narrow parts, coverage) · `regions [--n 8]` (open areas) · `at x,y ...` · `path x1,y1 x2,y2` · `plot out.png [--points f] [--crop x0,y0,x1,y1]` · `shot --out dir --view "px,py,pz:tx,ty,tz"` (real renders) · `coverage pts.json` · `prep` (precompute geometry for large scenes).
Fused maps have several trajectory segments: `info` lists them; pick one with `--seg` by `longestRun` and height range, and read `segCover` instead of `trackCover`. Scenes without a collision mesh work the same way: `info` says `geometry: estimated from the splats`. Look at `plot` before designing (the estimate misses some ground, for example under dense trees, and adds a little at the edges) and keep tracks on clearly walkable areas. The trajectory is where the scanner went, not always where a player can go: poses on chairlifts or vehicles are left out, and scenes without `info/poses.json` work too (`route()` then tours the open areas, `trackCover` is null; judge by `areaCover`).
